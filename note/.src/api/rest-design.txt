title: REST API design
about: The shape of an HTTP API: addresses, methods, bodies and status codes that other programs rely on.
## Addresses
- Nouns for resources (/orders/123), plural collections, no verbs in the path | S google-aip zalando-api
- Lowercase paths with hyphens, and one naming style for fields used everywhere | S zalando-api ms-api-guidelines
- Identifiers that cannot be guessed (random or time-ordered UUIDs), not running numbers | S rfc-uuid
- Nesting at most one level deep (/orders/123/items) | S google-aip
## Methods
- GET only reads and is safe to repeat | S rfc-http
- POST creates, PUT replaces, PATCH changes some fields, DELETE removes | S rfc-http
- PUT and DELETE give the same result when repeated | S rfc-http
- Actions that are not create, read, change or delete get their own sub-address with POST (/orders/123:cancel) | S google-aip
## Bodies
- JSON with a declared content type; dates as RFC 3339 text with a time zone | S rfc-datetime
- Money as an amount in the smallest unit plus a currency code (24500 and "SAR") | S iso-4217
- Only fields a caller may set are accepted; unknown or protected fields are refused | S owasp-mass-assignment
- Responses never include fields the caller may not see (password hashes, other customers) | S owasp-api-top10
## Status codes
- 200 done, 201 created with a Location header, 204 done with nothing to return | S rfc-http
- 400 bad input, 401 not signed in, 403 not allowed, 404 not found, 409 conflict, 422 checks failed | S rfc-http
- 5xx only for the server's own failures, never for the caller's mistakes | S rfc-http
## Reading efficiently
- Lists are paged from the first version | S google-aip-pagination
- Callers can ask for only the fields they need | S google-aip-fields
- ETag on reads so a client can ask "changed since?" and get 304 Not Modified | S mdn-etag rfc-caching
## Description
- The whole API described in an OpenAPI file kept in step with the code | S openapi
- Security reviewed against the OWASP API Top 10 before launch | S owasp-api-top10
