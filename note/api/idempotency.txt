IDEMPOTENCY AND RETRIES CHECKLIST: 14 items
Making it safe to send the same request twice, so a dropped connection never charges a card twice.
Backing: 0 Rule, 14 Standard, 0 Research, 0 Practice
Rule = a store or a law requires it · Standard = a published standard · Research = usability studies · Practice = good practice, no study found

KEYS
 1. Actions that create (payments, orders, messages) accept an idempotency key from the caller   (Standard: stripe-idempotency, aws-idempotent)  -> see backend/payments
 2. The same key with the same body returns the first result without doing the work again   (Standard: stripe-idempotency)
 3. The same key with a different body is refused with a clear error   (Standard: stripe-idempotency)
 4. Keys kept for at least 24 hours   (Standard: stripe-idempotency)

SERVER SIDE
 5. The key and the result saved in the same transaction as the work   (Standard: aws-idempotent)
 6. Two requests with the same key at the same moment: one waits or gets 409, never both run   (Standard: pg-locking)
 7. A database uniqueness rule as the last guard (one payment per order)   (Standard: pg-constraints)  -> see backend/payments, backend/database-design

RETRIES
 8. Clients retry only safe or idempotent requests   (Standard: rfc-http)
 9. Growing waits with a random spread and a maximum number of tries   (Standard: aws-backoff)
10. Retry only on errors that can pass (timeouts, 429, 503), never on 400   (Standard: google-aip-errors)
11. A timeout at every layer, each shorter than the layer calling it   (Standard: aws-backoff)
12. A circuit breaker stops calling a service that keeps failing   (Standard: fowler-circuit, sre-cascading)

MESSAGES AND EVENTS
13. Consumers handle the same message twice safely by remembering processed ids   (Standard: outbox)
14. Events written in the same transaction as the change (an outbox table), then sent   (Standard: outbox)  -> see backend/database-design
